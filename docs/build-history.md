**CHAT WITH A WARDEN — THE SOS QUIET LANE, WITH REAL WEB PUSH (2026-07-31, build clean, tsc clean, 33/33 rules cases green):** A third card under Call for Aid, LAST on the page on purpose — a chat window is the most inviting control there (costs nothing, commits to nothing, asks nobody to walk anywhere), so above the red button it would route people mid-emergency into a text queue. Threads hang off a call as `sos/{id}/messages/{msgId}`, so a dispatched emergency and a quiet question are the same machinery and a Warden can talk a party through while walking. **A SUBCOLLECTION AND NOT A FLAT `sosMessages`, for the rules-query reason:** a flat collection read with `where('sosId','==',x)` is refused outright — the filter does not prove every match qualifies, the same trap that shapes the `flags` rule — while gating on the PARENT leaves the subcollection query unfiltered and therefore answerable. **The central decision is `delivery`, and it is the opposite of every other push in the app.** Everything else is fire-and-forget with a swallowed catch, which is right for a booking mirror and a LIE in a conversation: the guest reads their unsent message sitting in the thread and stops talking, believing a Warden has it. A message is written LOCAL-ONLY as `pending` and only the SERVER moves it — resolve → `sent`, an adjudicated code (`pushError`, mirroring flagService's `CLAIM_REFUSALS`, fail-soft on anything unreadable) → `failed` with a retry under the ORIGINAL id, and **never settling → it stays `pending`, which is the truth**: with the persistent cache the SDK holds the write and will send it, but nobody has received it. That last case is why `reconcile()` exists — an offline write survives the tab closing, so the promise that would have resolved it is long gone by the time it lands, and the thread listener seeing the message come back FROM the server is the only acknowledgement that survives a reload. Cloud off entirely (`!isConfigured()`) reports ok, because there is no Warden to reach and no server that could ever acknowledge it; that is a different thing from configured-but-unreachable, which stays honest and stays pending. **COST MODEL: the thread listener lives and dies with the thread on screen.** A `collectionGroup('messages')` listener would charge every warden's screen for every message in the park, forever, to render a board showing one line per call; the board reads `lastMessageAt/From/Preview` stamped on the parent instead. Unread is derived per device from a local high-water mark (`ql:sosChatRead`) rather than a counter field — a counter means every thread open is a write racing the other side's write to the same doc. Board sorts kind-before-age (`urgency()`): a chat waiting an hour is still a question, an emergency raised ten seconds ago is a body in the woods — **verified in the console shot, the 1m22s emergency above the 9m12s question**. First reply IS the claim (auto-`acknowledgeSos`), because making a Warden press Dispatch as well just means two Wardens answer the same guest. **RULES, and the case the whole block exists for:** `from` is checked against WHO IS ASKING — a guest posting `from:'warden'` into their own thread would produce an official-looking answer in park livery from nobody at all ("the bridge is safe to cross"). Warden's line requires the roster, guest's requires the call; lines are WRITE-ONCE (update/delete refused for everybody including staff, same contract as `legs`) because what a Warden said at eleven at night has to still mean that tomorrow. **REAL PUSH, end to end.** `notificationService.systemNotify` only fires while a tab is running, which is useless for a conversation — the point is the answer reaching a guest on the trail with the screen off. Client `pushService` mints an FCM token and files it under the account; `functions/` (new, 2nd-gen, `onDocumentCreated`) is the only privileged code in the project and sends it. **Four things that are each a silent-failure trap:** (1) **two service workers, two scopes** — the push worker registers at `${BASE}fcm/` because a second registration at the ROOT scope REPLACES workbox's and takes the PWA's offline support with it; (2) **no Firebase SDK inside the worker** — the documented `importScripts` against gstatic is a live network dependency INSIDE the delivery path, and if it fails the worker throws before it has a `push` listener and the message is dropped with no banner and no error anybody sees; FCM delivers over ordinary Web Push and `onBackgroundMessage` is a wrapper around the `push` event handled directly, so the worker needs no SDK, no config, no network, and cannot drift from the npm `firebase` version; (3) **sends are DATA-ONLY** — a `notification` payload renders in the background AND fires the foreground handler, which is how one message becomes two banners; (4) the worker is kept **out of the precache** (`globIgnores`), because workbox would serve it cache-first and a service worker you can only update when another service worker feels like it is one you cannot ship a fix to (verified: `dist/firebase-messaging-sw.js` present, 0 occurrences in `dist/sw.js`). Token re-minted on every app start in both Shell and ConsoleScreen — the v9+ SDK dropped `onTokenRefresh`, so nothing else notices a rotated token and push dies silently; handed back on sign-out **sequenced before `cloudSignOut()`**, because the row is owner-scoped and a delete landing after auth is gone is refused forever. `pushTokens.staff` is a CLAIM (the collection is owner-writable), re-checked per uid against `staff/{uid}` by the sender — skipping that would hand every guest a live feed of every other guest's call for aid on their lock screen. `FCM_VAPID_KEY` is a SEPARATE export from `FIREBASE_CONFIG` on purpose: `isConfigured()` scans that object for `PASTE_ME` and an unset key in there would take Firestore, auth, sync and the console offline in one edit. **VERIFICATION — new `rules-tests/` (emulator, its own package so `firebase-tools` stays out of the app install): 33/33 green**, covering read (owner/staff yes, stranger/anonymous no), both directions of `from` spoofing, shape (`sosId` matches parent, body a non-empty string ≤2000, `createdAt` present), write-once against staff as well as the guest, demo-cast parity, and `pushTokens` ownership. **This reaches what the REST matrix structurally cannot** — every staff clause is `isStaff() && …` and `staff/{uid}` is `allow write: if false`, so no harness can mint a staff session against the live project; under the emulator `withSecurityRulesDisabled` seeds the roster and "staff may post as a Warden" / "a guest may NOT" are both actually asserted. BECAME A CONTROL (2026-08-01, build clean, tsc clean):** A reported delay — warden replies instant on the console, needing a screen change to appear on the guest — was investigated and turned out NOT to be a code fault.
